# P7 Integrated Delivery Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn P4's "seller delivers, buyer gives a code" into delivery tracked on the platform. Shops define zones and pickup points as data; buyers see honest fees and a promised date before ordering; every parcel becomes a shipment with a status machine, a rider, attempts and proof of handover; courier companies plug in through one `CourierProvider` port. BuyNSellem still owns no logistics and moves no money (umbrella positioning, Regulation 04/18): COD cash, courier fees and remittance are **recorded**, never ledgered.

**Architecture: hexagonal for couriers, exactly as P5 did for payments.** The whole domain — zones, quotes, shipments, handover, attempts, webhooks, jobs — is built against the `CourierProvider` **port** (`lib/delivery/types.ts`, mirroring `lib/payments/types.ts` and P5's `lib/payments/marketplace.ts`) and a deterministic scripted fake. The `manual` adapter (dispatchers and riders acting inside BuyNSellem) is the only adapter with behaviour; the `yango` adapter is a placeholder whose every method throws `CourierNotConfiguredError` and whose capabilities are all `false`; **no Campost file ships**. A registry (`lib/delivery/index.ts`, copying `lib/payments/marketplaceRegistry.ts`'s `adapterPresenceRefusal` idiom) refuses enabling `couriersEnabled` for an API-backed provider in production until a real adapter registers. A port **contract spec** (`runCourierContract`) pins the semantics every future adapter (Yango, Campost) must pass. Shipment status gets its own single writer, `services/delivery/shipmentTransitions.ts`; order effects flow through P4's `applyTransition` and nothing else; `shipment-events` is append-only and written only by the shipment services, in the same transaction as the change.

**Tech Stack:** Payload CMS 3.79 + MongoDB transactions (`packages/api`), Next.js 16 (`packages/web`), Expo SDK 57 (`packages/mobile`), Novu, Redis (rate limits + quote cache), Meilisearch (`packages/search-indexer`), vitest for the API (`bun run test:int` — never `bun test` there), `bun test` for web, mobile and search-indexer.

**Spec:** `docs/superpowers/specs/2026-09-15-p7-delivery-design.md` — the binding authority for every domain rule. Two of its assumptions are overridden by later decisions and the plan says exactly how: **B6** (maps) is replaced by the no-map-library rule, and **B7** (intercity COD) becomes a flag-driven data rule now P5 has shipped — see Global Constraints and the Conflicts section.

## Global Constraints

Copied from the spec, AGENTS.md and the standing project rules; every task's requirements implicitly include this section.

- **Hexagonal, strictly.** No service, route, job or test imports a concrete courier adapter; everything reaches a courier through `getCourierProvider(id)` from `lib/delivery/index.ts`. The `manual` adapter is internal-by-design (no network); the `yango` adapter is a disabled placeholder; in production, enabling `delivery.couriersEnabled` while an `active` courier names a provider with no registered working adapter is refused by a `courierAdapterPresenceRefusal` hook check, mirroring `adapterPresenceRefusal` in `lib/payments/marketplaceRegistry.ts`. The port's semantics live in one **contract spec** (Task 9) run today against the fake and the `manual` adapter, tomorrow against any real adapter unchanged. Adapter work for Yango/Campost is a later, separate work item.
- **B7 is a data rule, not a constant.** P5 shipped (flag-gated, off in production), so "intercity COD disabled" is expressed as `intercityCodRefusal(scope, paymentMethod): "cod_not_allowed" | null` in `services/delivery/quote.ts` — an `intercity` option with `paymentMethod: "cod"` moves to `unavailable` and placement refuses it with `checkout.methodUnavailable`; the same order paid protected (`mobile_money`, where `protectedPaymentEnabled`) passes. **No collection hook forces `codAllowed: false` on intercity zones**, no `INTERCITY_DISABLED` constant exists anywhere. (Everything intercity additionally stays hidden while `delivery.intercityEnabled` is false, which is production's state at P7's close.)
- **International rule.** Cities, districts, zones, fees, tariffs and ETAs are **data** (`lib/launchCities.ts` keys, `delivery-zones`, `couriers.tariffs`). No new country literal: the P5 ledger flagged the `Africa/Douala` schedule literal as debt — P7 adds exactly one named constant, `DELIVERY_TIMEZONE = "Africa/Douala"` in `lib/delivery/eta.ts`, consumed everywhere a delivery date is computed or formatted, documented as market data to lift with multi-market work. No other file spells the timezone or a city name.
- **Single writers stay single.** P4's `applyTransition` (services/orders/transitions.ts:285) remains the only writer of `orders.status` / `paymentStatus` / item fulfillment — P7 calls it from `shipmentTransitions.ts` and extends no transition table entry it doesn't name; `services/stock.ts` stays the only stock writer; `services/delivery/shipmentTransitions.ts` is the **only** writer of `shipments.status` and the only creator of `shipment-events` (a source scan pins this, Task 23). **P7 posts nothing to the ledger**: courier fees and COD remittance are records (`courierCost`, `codCollection`) — if any future money effect appears it goes through `services/ledger.ts` postings, never a direct write.
- **P6 is out; liability is data P6 reads later.** P7 produces, and pins by shape: `shipments.finalFailure {reason, at, returnInitiatedAt}`, `failureCostBearer` (`shop|reseller|supplier|buyer|none`), `codCollection` (`expectedAmount`, `collectedBy`, `collectedAmount`, `remittanceStatus` incl. `disputed`), `attempts[]`, `proof`, flags (`cod_remittance_disputed`, `return_overdue`), and `reports` rows (`targetType: shipment`, reasons `cod_remittance`, `return_overdue`). The proof-retention job consults `proofRetentionGuards` (an exported array of `(payload, shipment) => Promise<boolean>`; P6 pushes its open-dispute guard later; P7 ships the open-contest guard from P4's `handover.contestBy`).
- **No map library.** The spec's B6 (`react-native-maps`, Leaflet) is overridden: mobile captures GPS with `expo-location` ("Use my position") and opens external map URLs (`https://maps.google.com/?q={lat},{lng}`); web captures with `navigator.geolocation` and links out the same way. No tile rendering, no `GOOGLE_MAPS_ANDROID_API_KEY`, no `NEXT_PUBLIC_MAP_TILE_URL`, no new native build requirement. Plan nothing that needs a rendered map.
- **Retention.** `delivery-proofs` are purged 180 days after the shipment is terminal unless a retention guard objects — the `purgeDeliveryProofs` nightly job (Task 19), following `purgeVerificationData.ts`'s idiom.
- **Everything behind flags.** `AppSettings.delivery` defaults: `zonesEnabled: false`, `couriersEnabled: false`, `riderLinksEnabled: true` (effective only once `zonesEnabled`), `intercityEnabled: false`, `maxAttempts: 2`, `rescheduleHours: 48`, `pickupHoldDaysDefault: 7`, `gpsFarThresholdMeters: 300`, `providers.yango.enabled: false`. With `zonesEnabled` off, `quoteDelivery` serves P4's flat implementation unchanged and the migration can run safely first.
- **Error codes once, translated twice.** The 21 new codes are declared in `packages/api/src/lib/errors.ts`, FR/EN in `packages/web/messages/*` (`ApiErrors`) and `packages/mobile/src/locales/*` (`apiErrors`), parity specs extended (Task 1). Adapter errors never reach clients as text: routes map to `courier.notConfigured`, `courier.providerError`, `courier.cancelRefused` and log the original.
- **Locales own-only; vocab byte-parity.** Web strings live in a new `Delivery` namespace, mobile in `delivery`; neither task edits the other's namespaces. The shipment status table (buyer and seller wordings, FR/EN, verbatim from the spec), failure reasons and windows are mirrored label maps compared cell-for-cell in a new `shipment-vocab-parity.int.spec.ts` following `payment-vocab-parity.int.spec.ts` (explicit maps — no `t(\`ns.${variable}\`)`). Mobile interpolation `{{x}}`, web `{x}`.
- **Transactions and after-commit.** Multi-document writes use one Payload transaction via a shared `req` (`withTransaction`, `lib/transactions.ts:245`), retried on `TransientTransactionError`; SMS, Novu, Redis and provider calls go through `onCommit(commitContextOf(req), …)`. Shipment numbers come from `nextNumber(payload, "SHP", date)` (services/sequences.ts:70) **outside** the transaction — gaps allowed, same as order numbers.
- **Env vars in every compose file.** `YANGO_DELIVERY_BASE_URL`, `YANGO_DELIVERY_API_KEY`, `YANGO_DELIVERY_WEBHOOK_SECRET` enter `docker-compose.yml`, `docker-compose.local.yml`, `docker-compose.atlas.yml` **and** `deployments/docker-compose/docker-compose.yml` (the one the deploy workflow runs), empty-defaulted — the adapter is a placeholder, but the AGENTS.md rule is unconditional.
- **Ceilings (AGENTS.md), measured with the published commands on a quiet tree:** `check-types:tests` ≤ 105; `as never` in `packages/api/tests` ≤ 86; client casts (`packages/web/src`, `packages/mobile/src`, `packages/mobile/app`) ≤ 78; mobile advisory ≤ 35 **with a fresh `.expo/types/router.d.ts`**. None may rise; never republish a ceiling upward.
- **Runners:** `packages/api` is vitest via `bun run test:int` (never `bun test` there); web, mobile and search-indexer are `bun test`; `bun run generate:types` after any collection change, committed with it.
- **Assert a value, not an absence of complaint.** Counting, exact shapes, whole-object `toEqual` for wire shapes; every secrecy assertion paired with a positive one; every task carries at least one mutation step with the expected red.
- **Git:** one worktree per agent (AGENTS.md's recipe, including the `.env` symlinks); one-line commit subjects; no attribution trailers (`.husky/commit-msg` strips and fails them — never `--no-verify`); docs and comments in English, comments sparse.

## Review Focus

The five failure modes the spec implies that no single task's happy-path tests would exercise, most likely first. Each line's pinning test is assigned to the owning task.

1. **Two live shipments for one order.** A webhook-driven creation racing a manual one (or P8's purchase-order path racing the order path) must leave exactly one non-cancelled shipment — the unique partial index `(order) where status ≠ cancelled` plus the in-transaction pre-check, proven under `Promise.all`. → Task 11.
2. **Out-of-order and duplicate provider events.** A provider `delivered` arriving before `picked_up`, a duplicate `(provider, providerEventId)`, an event with `occurredAt` earlier than the last applied one, and an unmapped raw status: one state, one `shipment-events` row per fact, no transition for the disallowed ones — and a provider `delivered` with no verified code sets `handoverMethod: carrier_pod`, flag `delivered_without_code`, and opens P4's 48-hour contest window. → Task 17.
3. **Carrier switch racing the rider.** `POST /shipments/{id}/carrier` cancels and replaces in one transaction while the old shipment's rider taps "picked up": the conditional status write (the `applyTransition` idiom — `status: { equals: from }` in the update's `where`) must give one winner; the loser gets `shipment.invalidTransition` and the replacement is the only live shipment. → Task 15.
4. **Stock released exactly once, and only at physical return.** `failed` + `finalFailure` releases nothing; `returned` moves the order to `delivery_failed` and releases stock once; a replayed `returned` is refused; and a shipment leaving `pending` a second time (re-delivery) does **not** re-ship the order or resend the handover code. → Task 13 (return path), Task 11 (ship-once).
5. **Rider-link leakage.** The rider projection never contains `riderLink.tokenHash`, per-item prices, order totals beyond the COD amount, or buyer history (positive assertions on what it does contain, plus `JSON.stringify` scans); an expired/revoked/terminal token answers 404 `shipment.riderLinkInvalid` with no detail; the Redis limits (30/token/h, 60/IP/h) actually count. → Task 14.
